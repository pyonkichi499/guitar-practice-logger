# 設計判断

主な設計判断とその理由の記録。判断を変えたときは、古い記述を消さずに「見直し」として追記する。

## 前提となる目的

- 主な目的は、自分で聴き返して上達を確かめること。せっかくなので、毎日の記録は全部公開する。
- 毎日の手作業を最小にする。特に、ファイル名を手で付けない。
- GCP は、手間を減らすためではなく、触って学ぶこと自体が目的。

## 公開と音

### D1. 毎日全部を YouTube に公開する（2026-10-20）

- **理由**: 公開するかどうかを毎日選ぶと、その判断が手作業として残る。全部公開すれば判断がいらない。
- **却下した案**: 非公開を既定にして良いものだけ公開する。曲練習だけ公開する。

### D2. 公開版の音はギターとクリックだけにする（2026-10-20）

- **理由**: 市販曲のバッキングが入ると、YouTube の著作権の自動検出（Content ID）に引っかかり、ブロックや収益化への対応が毎回発生する。クリックなら著作権の問題がなく、リズムが合っているかの確認にも使える。
- **補足**: G2 FOUR から PC には、エフェクト後のギター音しか届かない（[調査結果](research.md)を参照）。そのため PC で鳴らしたクリックは録音に入らず、DAW の書き出しに含める。
- **却下した案**: G2 FOUR 内蔵のリズム機能（USB の録音に乗るか未確認で、PC のバッキングとも同期しない）。

### D3. バッキングと混ぜた版は今は作らない（2026-10-20）

- **理由**: 今は必要ない。将来混ぜられるように、DAW ではバッキングをプロジェクトの先頭に置き、先頭から書き出して頭を揃えておく。

## 録音と取り込み

### D4. 練習の最後に、メニューごとに 1 本ずつ録る（2026-10-20）

- **理由**: 練習を丸ごと録ると、聴き返すときに頭出しがしにくく、曲ごとの上達も追いにくい。

### D5. 曲は書き出し先の曲フォルダで決める（2026-10-21）

- **理由**: 書き出し先を選ぶ操作が曲の選択を兼ねるので、ファイル名の入力も一覧からの選択もいらない。1 回の取り込みで各曲 1 本までという制約は、1 日 1 本という運用と一致する。
- **見直しの経緯**: 当初は「1 つの受付フォルダに書き出し、直後に一覧から曲を選ぶ」案だった。続けて書き出すと上書きされるので、書き出すたびにスクリプトを動かすか、常駐させる必要があった。曲フォルダ方式なら、最後に 1 回取り込むだけで済む。
- **受け入れたリスク**: 取り込みを忘れたまま翌日に同じ曲を書き出すと、前日分は上書きされる。

### D6. BPM は取り込み時に手で入力する（2026-10-21）

- **理由**: クロマチックは上達に合わせて BPM を上げていき、曲でもテンポを落とす日がある。曲ごとに固定の BPM を持つのでは記録にならない。前回の値を初期値にして、変えない日は Enter だけで済むようにした。
- **却下した案**: クリック音から BPM を推定する（誤検出の恐れがある）。ファイル名に BPM を入れる（手で名前を付けることになる）。

### D7. 録音日はファイルの更新日時から取る（2026-10-21）

- **理由**: 取り込みの実行日だと、取り込みが翌日にずれたときに日付が狂う。

### D8. テイクの記録は SQLite。WAV にも同じ情報を持たせる（2026-10-21）

- **理由**: 集計や「未公開のテイク」の検索がしやすい。DB は WSL2 側に置く（`/mnt/c` 上の SQLite はロックの不具合が出やすいため）。
- **WAV にも持たせる理由**: DB にはバックアップがない。曲・録音日・BPM をファイル名と WAV のメタデータの両方に入れておけば、DB が消えても GDrive 上の WAV から作り直せる。

### D9. 曲は登録コマンドと台帳（TOML）で管理する（2026-10-21）

- **理由**: フォルダ名は英数字の ID にし、表示名などは台帳に持たせる。曲名を変えても過去の記録とのつながりが切れない。台帳は Git で管理できる。

## 実行環境と構成

### D10. 取り込みは WSL2 で動かし、`/mnt/c` を読む（2026-10-21）

- **理由**: 開発環境と同じ場所で動かせる。扱うのは 1 日数本の WAV なので、`/mnt/c` が遅くても問題にならない。パスは設定ファイルで切り替えられるようにし、Windows 側に移す余地を残す。

### D11. GDrive への保存は Drive API で行う（2026-10-21）

- **理由**: 実行環境に左右されず、GCP に移すときもそのまま使える。
- **却下した案**: Google ドライブ（パソコン版）の同期フォルダ。API が不要になるが、WSL2 からは扱いにくく、GCP への移行にも使えない。

### D12. GCP はまずローカルで完結させてから移す（2026-10-20）

- **理由**: 小さく始められる。2-A は、処理の本体を保存先や起動方法と切り離して作り、移すときの作り直しを減らす。

### D13. 設定ファイルはリポジトリ直下の `config.toml`（2026-10-21）

- **理由**: リポジトリの外（`~/.config`）を触らずに使い始められる。個人のパスを含むので Git 管理外にする。

## 保留事項

| 項目 | 決めるタイミング | 判断材料 |
|---|---|---|
| 録音の実行環境（Windows / WSL2） | Phase 2-B または 3 の着手時 | WSL2 からの録音は不安定。GUI の方針とあわせて決める |
| OAuth 同意画面のモード | Phase 2-A の着手時 | テストモードだとログインが 7 日で切れる。本番モード（未審査）なら切れないが、初回に警告が出る |
| DB の既定の置き場所 | 随時 | リポジトリ内（Git 管理外）に置けば、すべてがリポジトリ内で完結する |

# 設計判断メモ

練習記録パイプラインのフェーズ分けと全体方針について、壁打ち（2026-10-20）で合意した内容。

## 目的

- 主目的は自分で聴き返して上達を確認すること。せっかくなので毎日全部を公開する。
- 日々の運用の手作業を最小にする。特に、ファイル名を手で付けない。

## 決定事項

| # | 項目 | 決定 |
|---|---|---|
| 1 | 公開範囲 | 毎日全部を YouTube に自動で公開する |
| 2 | 公開版の音 | ギターとクリックのみ。バッキングは入れない（Content ID 回避） |
| 3 | 録音単位 | 練習の最後に、メニュー（クロマチック、曲ごと）を1本ずつ録る |
| 4 | バッキングと混ぜた版 | 今は作らない。将来混ぜられるよう、DAW ではバッキングをプロジェクト先頭に置き、先頭から書き出す |
| 5 | クリック | DAW のクリックを書き出しに含める |
| 6 | 曲・BPM・日付 | 書き出し直後に受付スクリプトで入力する。曲は登録済み一覧から選ぶ。BPM は手入力で、初期値はその曲の前回値。日付は自動で付ける。BPM の自動推定はしない |
| 7 | ファイル管理 | DAW は受付フォルダに既定の名前で書き出す。受付スクリプトが日付付きの名前で退避し、処理が済んだら処理済みフォルダへ移す |
| 8 | 動画 | 背景画像に日付・曲名・BPM を ffmpeg で描画した静止画動画にする |
| 9 | GCP | 学ぶこと自体が目的。まずローカルで完結させ、後から移す |

## フェーズ

1. **Phase 1**: DAW（Cakewalk Next）で録音し、受付スクリプト（曲と BPM の入力、退避）を使い始める。上書きを防ぐため、これを最初に作る。
2. **Phase 2-A**: 動画化、GDrive への保存、YouTube への公開。Phase 1 の間にたまった分をまとめて処理し、テストデータとしても使う。
3. **Phase 2-C**: 処理の本体を GCP（GCS、Cloud Run、BigQuery など）に移す。2-A は保存先や起動方法と処理の本体を分けて作っておく。
4. **Phase 2-B / Phase 3**: DAW をやめて録音もスクリプト化し、GUI を付ける。受付スクリプトの曲選択と BPM 入力が GUI の原型になる。

## 保留事項

- **実行環境（Windows / WSL2）**: 2-B か Phase 3 に着手するときに、GUI の方針とあわせて決める。WSL2 からの録音は不安定なので、録音は Windows 側で行う前提。受付スクリプトと後処理はどちらでも動く形で作る。
- **OAuth 同意画面のモード**: 2-A で API を試すときに決める。テストモードだとリフレッシュトークンが7日で失効する。
- **プレイリスト**: 種別・曲ごとの自動プレイリスト化は将来の課題。

## 調査で分かった事実（2026-10 時点）

- **ZOOM G2 FOUR**: USB は 2in/2out、44.1kHz 固定。PC へ送られるのはエフェクト後のギター音のみ。PC の再生音は本体のモニターに混ざるだけで、録音側には戻らない（ループバックなし）。Windows では専用ドライバが必要。
- **WSL2 での録音**: WSLg（RDP 経由）や usbipd での録音は品質・遅延・安定性に不安があり、録音は Windows ネイティブで行うのが確実。
- **YouTube Data API**: 公式文書によれば、未監査プロジェクトでも動画が強制的に非公開にはならなくなった（要実機確認）。videos.insert は専用クォータで既定 100 回/日。
- **Google Drive API**: サービスアカウントにはストレージ容量がないため、個人の My Drive には使えない。インストール型アプリの OAuth（ユーザー認証）を使う。

## 要確認

- 公開設定でのアップロードが API 経由で実際に通るか（最初に1本試す）。
- Cakewalk Next で、書き出し先と既定のファイル名がプロジェクトにどこまで保存されるか。
